## Architecture Decisions

1. **Fixed table over configurable percentages**: The official guide has exact values that don't follow clean percentage patterns. A lookup table is simpler and more accurate than trying to derive them from base percentages.
2. **Automatic time bonus over checkboxes**: The timer already tracks time, so computing the bonus automatically is more accurate and less work for the judge.
3. **No attire points**: The guide says "to avoid disqualification or point loss" — it's a requirement check, not a scoring category. Kept the checkboxes for visual verification but removed points.
4. **Kept old Settings type**: Didn't break backward compatibility with stored settings. Old fields just become unused.

## Honest Feedback

1. **I designed a scoring system without the spec.** The user had an official scoring guide the whole time. I created a configurable percentage-based system because I didn't ask for the rules. This is the "building before understanding" anti-pattern. The user had to come back and say "here are the actual rules" which invalidated all the grade percentage settings work.

2. **The Edit tool for large data blocks is fragile.** I used Edit to replace the scores array in demoData.ts but the old_string only matched the beginning. The rest of the old data was left as garbage. For large data rewrites, I should use Write to replace the entire file, or be much more careful about matching the complete block.

3. **I debated field naming too long.** Whether to rename `attireScore` to `timeBonus`, whether to remove old Settings fields, whether to change ScoreBreakdown. These are low-stakes decisions that I spent disproportionate mental energy on. The right move was to just pick the pragmatic option (keep old fields, add new ones) and move on.

## Lessons Learned

- Always ask for the official specification before designing a scoring/calculation system. Guessing leads to throwaway work.
- Use Write (full file replace) for large data block replacements, not Edit (partial match).
- For type migrations in persisted data (localStorage), keep old fields with fallback values rather than breaking backward compatibility.
